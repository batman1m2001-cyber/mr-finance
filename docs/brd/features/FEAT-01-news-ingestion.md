# FEAT-01 — News ingestion and gates

| | |
|---|---|
| Type | BRD capability |
| Requirements | BRD-BR-01, BRD-BR-02, BRD-BR-04, BRD-FR-101, BRD-FR-102, BRD-FR-104, BRD-RULE-WF-01, BRD-RULE-DATA-04 |
| Users | Machine (scheduled); CIO sees the result in the inbox (FEAT-02); Compliance sees held items (SCR-CMP-01) |
| Entry points | Job `news_ingest` every 10 min; `POST /api/news/ingest`; `uv run operonx run news_ingest` |
| Status | see [traceability](../requirements/requirements_traceability.md) |

## Purpose
Bring public news into the system within minutes, refuse what may not be used, hold what Compliance must see
first, and sort the rest so the CIO reads the important items first. It produces no opinion and touches no
client data.

## Preconditions and permissions
- The white list and gates in `data/news_config.json` (version NEWS-DEMO-2026-10, generated by
  `scripts/make_news_config.py`, owned by Compliance per BRD §13.1). No user is needed to fetch.

## Inputs → outputs
- **In:** every approved source's RSS/Atom feed (11 configured; title, summary, link, published time).
- **Out:** `news_items` rows (`NW-000nnn`), each with source, kind (`intl`/`domestic`), engine factors it
  touches, relevance (`high`/`medium`/`low`, with a score), an event-type hint, `published` and `ingested`
  timestamps, a `status` (`new`, `grouped`, `dismissed`, or `refused` for an item that failed a gate — kept aside,
  out of the inbox) and a `held` flag; and a `news_runs` record per fetch (per-source counts, refusals, errors).

## Behaviour
1. `fetch` — read every white-listed feed concurrently; a broken feed is recorded and the others continue.
2. `screen` — each item through the gates, in order; the first failure decides:
   source on the white list → link on the source's own site → has a published time → published ≤ 10 minutes
   after ingestion (else **refused**, never pulled back; BRD F20) → not older than 7 days (else **skipped**).
3. Restricted list: an item naming a restricted organisation (whole-word, case-insensitive) is **held** for
   Compliance (BR-04).
4. `keep` — classify: international or domestic (by source, then words); factors from `factor_words`; relevance
   and event type from `event_types`; drop duplicates by normalised URL and by title.
5. Each kept item and each run is written with an audit row.

## Rules and validation
Implemented in `src/news/rules.py` (pure): `gate`, `classify`, `url_key`, `title_key`. Settings
`future_minutes = 10`, `max_age_days = 7`, `fetch_timeout_s = 15`.

## Errors
A page that is not a feed is a source error in the run record; it does not fail the run. Refused items are kept
with status `refused` and their reason (never shown in the inbox); skipped (too old) items are only counted.

## API and data
- `POST /api/news/ingest {}` → the run's counts (service `news_fetch`, graph `ingest_flow`).
- `GET /api/news/inbox` → items and feed health (FEAT-02).
- Tables: `news_items`, `news_runs` ([domain model](../architecture/domain_model.md)).

## Implementation
`src/news/rss.py` (RSS 2.0/Atom → plain items), `src/news/rules.py`, `src/news/ops.py` (`fetch`, `screen`,
`keep`), `src/news/graph.py` (`ingest_flow`), `src/news/store.py`; job and service in `app/main.py`.

## Dependencies
Outbound HTTPS to the feeds ([integrations](../architecture/integrations.md)). FEAT-11 (audit).

## Limitations
- The white list is a generated file, not versioned configuration with an approval step (FR-701, FEAT-14).
- No alert is raised when a feed fails (NFR-12): failures show in the inbox's feed-health strip only.
- The scheduled job runs inside `operonx serve`; the live demo's “≤ 10 minutes” holds only while it runs.
