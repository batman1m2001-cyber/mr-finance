# Moving to the bank's database and WORM storage

**For:** the bank's engineers who move OneWealth from the demo's SQLite file onto the bank's PostgreSQL and
write-once storage. **Rule:** BRD-RULE-DATA-10 (§11.4). **Decision:** [ADR-0025](../decisions/ADR-0025-postgresql-export-and-worm-audit.md).

The demo keeps one SQLite file. What is proven here is that its data moves to PostgreSQL losslessly, with the JSON
fields the product reads by field split into columns and tables, client values still encrypted, and the audit log on
write-once storage. Running the application on PostgreSQL is the bank's port, and section 5 lists what changes.

## 1. Export and check in one command

```bash
# the state file MF_STATE names (default data/state.db), read only; MF_DATA_KEYS set when it is sealed
python scripts/export_postgres.py --out export.sql            # the load file: schema, then COPY per table
psql -v ON_ERROR_STOP=1 -d onewealth -f export.sql            # into an empty database, one transaction

# or prove it end to end against a throwaway PostgreSQL in Docker (no port opened; reached by docker exec)
python scripts/export_postgres.py --docker mrf-pg --start postgres:16-alpine --stop --report check.json
```

The check (`control/pgexport.py::compare`) compares, per table:

- rows in PostgreSQL against rows in SQLite (children against what the split produces);
- the sum of every number column, by SQL on each side;
- **every row, read back from PostgreSQL**, put back together with its child rows (`rebuild`), every sealed value
  opened, compared with the SQLite row opened. One changed character in one row fails it. This was tested by editing
  a child value, a split column and one market price in PostgreSQL: each was named.

Measured on the demo's development database (2026-10-16, PostgreSQL 16.15): 35 tables (47,793 rows, 46,159 of them
market prices) and 15 child tables (1,516 rows), a 14 MB load file written in 1 s, loaded in 2.8 s, checked in 25 s. The same
with client data sealed: the same times, and no client name or account number anywhere in a `pg_dump` of the result
(the plain export, as a control, contains them).

## 2. The mapping

| SQLite | PostgreSQL |
|---|---|
| `text` / `real` / `integer` | `text` / `double precision` / `bigint` |
| `integer primary key autoincrement` | `bigint generated by default as identity`, its counter set past the largest id |
| a JSON `data` column | `jsonb`; `text` where a client value is sealed whole (`crypto.COLUMNS`: people, sources, holdings, profile, results, reviews, family results) |
| `external_outputs.body` | `text`, byte for byte: its hash was taken over that text |
| primary keys, unique constraints, indexes | kept, same names |

Money is stored as whole đồng in JSON numbers and `bigint`; `jsonb` keeps numbers exactly.

### JSON fields made columns

A field a query filters on becomes a column of its table, with an index.

| Table | Columns | Read by |
|---|---|---|
| `agent_runs` | `status`, `error`, `finished` | the agents' recent runs (`views/store.py`) |
| `agent_jobs` | `started` | jobs running too long (`views/queue.py`) |
| `policy_documents` | `source_url` | one document per source (`policy/store.py`) |

### JSON lists and maps made tables

Each child table's key is the parent's key plus `pos` (the list order) or the map key, with `on delete cascade`.

| Child table | From | Columns besides the key |
|---|---|---|
| `view_history`, `config_version_history`, `policy_document_history`, `newsletter_history`, `alert_history`, `application_run_history`, `news_item_history` | each record's `history` | `at`, `by`, `status`, `note`, `data` (the rest) |
| `event_news`, `event_factors` | an event's news and factors | `news_id` / `factor` |
| `news_item_factors` | a news item's factors | `factor` |
| `newsletter_views` | a newsletter's views | `view_id` |
| `run_snapshot_families` | a snapshot's families (by family id) | `data` |
| `application_run_ranking` | a run's ranking | `family_id`, `data` |
| `family_impact_holdings` | a family result's holdings | `data` |
| `client_transactions` | a source's transactions | `data` |

**Lossless by construction:** a value is split only when it has the expected shape — a non-empty list of objects,
a list of strings, a string or a decimal for a column. Anything else (an empty list, a number where a string was
expected) stays in `data` as it was. An item's field goes to a column only when it has that column's type; a `null`
stays in `data`. So the row put back together is the row that was exported, which the check proves.

## 3. Encryption at the bank

- **Sealed values move as they are.** A sealed value's associated data is its table, primary key and column
  (`crypto.where`), not a SQLite row number, so a sealed column that is not split is copied unchanged and opens in
  PostgreSQL with the same keys.
- **A split value is sealed again where it lands.** A sealed source (a family's holdings, a source's transactions,
  a snapshot's families, a run's ranking) is opened with the keys, and each child's `data` is sealed at the child's
  own place (`client_transactions/C01/vps/3/data`): moved to another row, it does not open. The ids that make the
  keys (family id, position) stay plain, as `people.id` is.
- **The export needs the keys** for a sealed database (`MF_DATA_KEYS`, from the secret store in production). Without
  them it stops and says so; it never writes plain what was sealed.
- Rotation (`scripts/rotate_keys.py`) works by the same places; ported to PostgreSQL it adds the child tables'
  `data` columns to `crypto.COLUMNS`.

## 4. The audit log on write-once storage

The database's hash chain shows a changed row unless whoever changed it recomputed every hash after it — which
anyone able to write the database can do without the HMAC key. Write-once segments close that
(`src/control/worm.py`):

- The hourly `audit_check` job, after the chain checks, copies the rows added since the last segment into a new
  file `audit-<first>-<last>.jsonl`: a header (first and last row, the SHA-256 of the previous segment, the chain
  hash of the last row) and one line per row. The file is written under a temporary name, made read-only, and
  published by a hard link, which fails if the name exists: no segment is ever overwritten or appended to.
- The same job walks every segment: read-only, chained to the one before by file hash, its rows a valid run of the
  chain, and **every row still the same in `audit_log`**. A row changed after it was segmented, with the whole chain
  recomputed so the database's own check passes, is named (tested). A segment edited, removed or left writable
  breaks the walk (tested). Either raises the “audit chain” alert for Compliance and Admin; nothing is added on top
  of a broken record.
- `/healthz` lists `audit_worm`; the System page shows the segments and the last row they hold.

**At the bank** the folder becomes a bucket with S3 Object Lock (or the bank's WORM appliance) in **compliance
mode**, the retention the bank's rules set (BRD-NFR-09). Compliance mode is what makes “never again” hold against
an administrator, which a read-only file on a disk the administrator owns cannot:

```bash
aws s3api put-object --bucket onewealth-audit --key audit-0000000001-0000000451.jsonl \
  --body audit-0000000001-0000000451.jsonl --object-lock-mode COMPLIANCE \
  --object-lock-retain-until-date 2036-10-16T00:00:00Z --checksum-algorithm SHA256
```

`worm.write` and `worm.verify` take the folder as an argument; the port replaces the file calls with the bucket's
put (with `If-None-Match: *`, so an existing key is refused) and list/get.

## 5. Porting the application to PostgreSQL

The schema, the data and the audit log are proven above. Running the code on PostgreSQL changes these places
(counted 2026-10-16):

| SQLite construct | Where | PostgreSQL |
|---|---|---|
| `sqlite3.connect` (26 calls, 9 files) | `control/db.py`, the stores | one connection pool (psycopg 3) behind `db.tx()` |
| `begin immediate` (4) | `control/db.py`, stores | `begin isolation level serializable`, or an advisory lock where a counter or the audit sequence is taken |
| `insert or replace` (5), `insert or ignore` (5) | stores | `insert … on conflict (…) do update` / `do nothing` |
| `json_extract` / `json_remove` (4) | `views/store.py`, `views/queue.py`, `policy/store.py`, `apply/run.py` | the split columns of §2; `data - 'families'` |
| `pragma`, `executescript` (8) | schema set-up | the DDL from `export_postgres.py --schema`, under a migration tool |
| `lastrowid` (2) | `market/store.py`, `news/store.py` | `insert … returning id` |
| triggers refusing `update`/`delete` on `audit_log` | `control/audit.py` | the same as a PL/pgSQL trigger, plus `revoke update, delete` from the application's role |

Reads of the split fields go to the columns and child tables; writes build them with `pgexport.split`, which is
the reference for every field's place. The tests reach the data through `db.tx()` and the stores; the two test
files that open the SQLite file directly (sealed bytes on disk, a forced edit of the audit log) prove SQLite-specific
behaviour and are rewritten for PostgreSQL with the port.

## 6. Order of the move

1. Freeze writes (the scheduler stopped, the web app read-only), take the final `audit_check` so every audit row
   is in a segment.
2. `export_postgres.py --out export.sql` with the production keys from the secret store; load it; run the check
   against that database (`compare` with a reader on it) and keep the report.
3. Upload the segments to the locked bucket; run `worm.verify` against the bucket and the new database.
4. Start the ported application on PostgreSQL; `/healthz`, the System page and the audit check must be green
   before writes are opened again.
